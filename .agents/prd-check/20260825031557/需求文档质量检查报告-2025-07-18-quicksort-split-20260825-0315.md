## 深度洞察

> 三维度检查回答了「文档写得怎么样」，以下洞察回答「文档缺了什么」。

### 缺失的隐含需求

1. **排序方向与稳定性**
   - 证据：文档「当前理解」章节描述了「实现一个快速排序算法」，但未提及排序方向（升序/降序）、是否稳定排序（保留相等元素相对顺序）。
   - 缺失：排序方向（升序/降序）和稳定性要求是排序功能的隐含需求——任何排序实现都必须明确这两点。文档第 4 个问题提及了稳定性但作为可选问题，未得到回答。
   - 后果：如果忽略，开发可能默认实现升序，后续需求方要求降序时需返工；稳定性缺失可能导致业务数据在排序后出现非预期的顺序变化。
   - 建议：补充排序方向（默认升序，支持通过 Comparator 自定义）和稳定性声明（快速排序通常不稳定，若业务需要稳定排序需特殊处理或改用归并排序）。

2. **边界情况与异常处理**
   - 证据：文档全文未提及任何边界情况处理。
   - 缺失：空数组/null 输入、单元素数组、全部重复元素、已排序/逆序数组等边界情况是排序算法的隐含需求——每个排序实现都必须处理这些场景。
   - 后果：如果忽略，可能导致 NPE（null 输入）、栈溢出（已排序数组在朴素快排中退化为 O(n²)）、或无限递归。
   - 建议：补充边界情况处理策略：① null 输入 → 抛出 `IllegalArgumentException` 或返回空列表；② 空数组/单元素 → 直接返回；③ 重复元素 → 正常处理；④ 已排序/逆序 → 随机化 pivot 或三数取中避免退化。

3. **与 Java 内置排序的关系**
   - 证据：文档「当前理解」章节描述了仓库为 Spring Boot / Java 17 项目，但全文未提及 Java 标准库已内置 `Arrays.sort()`（Dual-Pivot Quicksort）和 `Collections.sort()`（Timsort）。
   - 缺失：文档未说明为何需要自定义实现而非使用标准库——这是「实现排序算法」需求的隐含前提。
   - 后果：如果忽略，开发完成后可能被质疑「为什么要重复造轮子」，浪费开发资源。若确实有特殊需求（如教学演示、自定义比较逻辑），未说明会导致方案评审时被驳回。
   - 建议：补充「为什么不用标准库」的说明，明确自定义实现的必要性（如：学习目的、特殊排序策略、标准库不满足的约束）。

### 跨章节矛盾

1. **集成深度假设冲突**
   - 矛盾：「当前理解」章节推断快速排序可能作为「工具类/服务方法」加入项目（暗示轻量集成），但「暂定影响地图」同时列出了控制器、服务层、模型层、测试、构建配置五个领域的变更（暗示深度集成）。
   - 需明确：到底是轻量工具类（仅新增一个 Java 文件）还是深度集成（涉及 Controller → Service → Model → View 全栈改动）？回答第 1 个关键问题后即可消除此矛盾。

### 实现可行性疑点

1. **递归深度与栈溢出风险**
   - 疑点：文档第 4 个问题提及「需要处理大数据量，关注栈溢出」，但朴素快速排序在极端情况下（已排序数组 + 固定选择首元素为 pivot）递归深度可达 N，导致 `StackOverflowError`。
   - 建议：若需要处理大数据量，补充实现约束：① 使用三数取中或随机 pivot 避免退化；② 考虑尾递归优化或迭代实现；③ 设定最大数据量阈值及降级策略（超过阈值切换为 `Arrays.sort()`）。

2. **现有仓库无排序业务场景**
   - 疑点：文档明确指出「仓库中目前没有任何排序相关功能，也没有明确的数据排序业务场景」。在无业务场景的情况下实现排序算法，功能完成后可能无法验证其业务价值。
   - 建议：在进入开发前，先回答第 1 个关键问题（目标用户和场景），确保排序功能有明确的业务落脚点。
